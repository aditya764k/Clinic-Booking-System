# Module 1 — Data Layer & Core Domain Model: Detailed Summary

## Overview

Module 1 establishes the **entire database foundation** for the Clinic Appointment Manager. It is a pure infrastructure module — no API endpoints, no business logic — just the schema, ORM models, migration history, and a verification harness. Everything built in future modules (auth, booking, billing) will sit on top of this layer.

## Key Technical Approaches & Design Decisions

### 1. SQLAlchemy 2.0 Native Typing (`Mapped[T]` + `mapped_column()`)
The models were written (and later **refactored**) to use the full SQLAlchemy 2.0 declarative syntax:
```python
# Old (1.4 style, causes IDE errors with DeclarativeBase):
id = Column(Integer, primary_key=True)

# New (2.0 style, fully typed, IDE-friendly):
id: Mapped[int] = mapped_column(primary_key=True)
```
This gives full IDE autocompletion, Pylance/Pyright type checking, and is the production standard for all new SQLAlchemy 2.x projects.

### 2. Native PostgreSQL ENUMs (not plain VARCHAR)
Every status/role field is backed by a **real Postgres ENUM type**, not a string:
```python
role: Mapped[UserRole] = mapped_column(
    SAEnum(UserRole, name="userrole", create_type=True)
)
```
This means the DB enforces valid values at the **storage engine level** — invalid strings are rejected before they even reach application logic.

**4 Postgres ENUM types created:**
- `userrole` — `patient`, `receptionist`, `doctor`
- `appointmentstatus` — 8 values (`booked` → `no_show`)
- `invoicestatus` — `pending`, `paid`, `failed`
- `paymentmethod` — `razorpay`, `cash`

### 3. `TIMESTAMP WITH TIME ZONE` Everywhere
All timestamps use `DateTime(timezone=True)` — mapping to Postgres's `TIMESTAMPTZ`. This stores UTC offset with every timestamp, preventing timezone-related bugs when users/servers are in different zones.

### 4. Composite Unique Constraint for Anti-Double-Booking
```python
__table_args__ = (
    UniqueConstraint(
        "doctor_id", "slot_start",
        name="uq_appointment_slots_doctor_slot_start"
    ),
)
```
This is the **central business invariant** of the system: a doctor cannot have two appointments starting at the same time. This is enforced at the **Postgres level**, not the application level, so even a race condition between two concurrent API requests cannot produce a double-booking.

### 5. `TYPE_CHECKING` Guard for Circular Import Prevention
All cross-model type references use `TYPE_CHECKING`:
```python
if TYPE_CHECKING:
    from app.models.identity import PatientProfile, DoctorProfile
```
This avoids Python circular import errors at runtime while still giving the type-checker (Pylance, mypy) full visibility into the relationship types.

### 6. Alembic Autogenerate Migration
Alembic's `--autogenerate` was used to produce the migration by introspecting `Base.metadata`. The `alembic/env.py` was wired to import all models (via `app.models`) before `Base.metadata` is read, ensuring all 9 tables are discovered. The generated migration was then **enhanced** to also drop ENUMs in the `downgrade()` function.

### 7. `database.py` — Dual-Environment DATABASE_URL Resolution
The engine setup intelligently finds the `.env` file in multiple locations:
```python
# Priority order:
1. DATABASE_URL already in environment (Docker injects via env_file)
2. clinic-app/.env   (local dev running from host)
3. backend/.env      (fallback)
4. ./.env            (cwd fallback)
```
This allows the same code to work both **inside the Docker container** and **locally** without any code changes.

### 8. `models/__init__.py` as Alembic Discovery Hub
```python
from app.models.identity import User, PatientProfile, DoctorProfile
from app.models.scheduling import AppointmentSlot
from app.models.appointment import Appointment, ClinicalNote
from app.models.billing import Invoice, WebhookEvent
from app.models.audit import AuditLog
```
Alembic's `env.py` imports this single file, which causes all models to register themselves against `Base.metadata`. Without this, `--autogenerate` would produce empty migrations.

## Verification Script: `scripts/verify_module1.py`

The verification script exercises the **entire data chain end-to-end** inside the live Docker+Postgres environment:

```
Step 1: Insert 3 Users (patient / receptionist / doctor role)
Step 2: Insert PatientProfile + DoctorProfile
Step 3: Insert AppointmentSlot
Step 4: Insert Appointment linking all of the above
Step 5: Re-query via ORM relationship navigation (confirms lazy-load works)
Step 6: Attempt duplicate (doctor_id, slot_start) → assert IntegrityError
```

**Final result (verified live):**
```
Chain insert:              PASS ✅
Duplicate-slot constraint: PASS ✅
```
